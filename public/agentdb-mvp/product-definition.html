AgentDB Data Store

The second product on the data store — loading warehouse tables into AgentDB on a schedule. Worked in sequence, because each stage below is derived from the one above it rather than decided on its own.

Two products sit on the data store. Pulse caches a whole model in one click — built, shipped, frozen. Data Store loads individual warehouse tables on a schedule, and is what this is about. Same storage underneath; two ways to fill it.

An interface already exists — nine screens from an acquired product, with a three-step extract wizard. What doesn't exist is the reasoning underneath it. The risk of starting from those screens is that we inherit a scope that was set for someone else's product.

Stage 1

What it is, its boundaries, its value here

Everything downstream depends on this being right, so it is worth being slow.

What it is

The definition I'd argue for Proposed

Not a general ETL tool. A loading step for analysis.

Fivetran is general purpose — any source, any destination, any purpose. Ours is narrow, and every part of that narrowness buys a simplification:

  • We know the destination, so there is no destination to configure.
  • We know the purpose, so a column can be described by what you can chart, not by SQL types.
  • We know what happens next — a model gets built — so loading can hand off into modeling rather than ending at "table loaded."
  • Warehouse connectors only. No SaaS sources, so no connector library to maintain.
  • We are not a transformation tool, so SQL hooks are a candidate to cut.

This is the sentence that lets us delete what the acquired product carries.

Its boundaries

Three borders, and two of them are internal. The internal ones matter more, because that is where we will accidentally build the same thing twice.

Border 1

Against Fivetran

They consolidate at the source level — apps and operational databases that were never in a warehouse. We move data out of a warehouse into ThoughtSpot, one step later in the chain. Many customers already used Fivetran to fill the Snowflake we now read.

Not our problem: scattered source data.

Border 2

Against Data Studio

Data Studio is being built with modeling, exploration, testing and data cleaning. So cleaning has a proper home one step later.

The line: the loader's job is fidelity — get the data here intact. Data Studio's job is shape and meaning.

Border 3

Against Pulse

Pulse caches a model. Data Store loads a table. Both fill the same store and both cut cost.

Unsettled — see the overlap question below. This is the border a customer will actually stand on.

Why the Data Studio border is the important one Known

Anything the loader does to data on the way in is something Data Studio then has to work around or undo, and a column cleaned in two places is a column nobody can trace.

This is the same conclusion the industry reached moving from ETL to ELT, for the same reason: separate the stable act — moving bytes — from the volatile one — deciding what they mean. Definitions change constantly; extraction doesn't.

Which makes the loader's feature list shorter than the acquired product's, not longer.

Its value in ThoughtSpot's context

DriverPulseData Store
Cut the warehouse bill, and be faster Yes — model grain, one click Yes — table grain, configured
Analyse data that can't be queried live at all No Yes, and only this — cross-warehouse joins, unsupported sources

Cost is the shared driver, and probably the most common one for both. A company looks at its BI bill, sees what the warehouse charges, and wants it down. Either product does that, so a customer arriving with that problem could reasonably be sent to either.

What the Data Store adds is capability — analysis otherwise impossible, most obviously joining tables in two different warehouses, which no live query can do. Unique to it, but not the only reason to want it.

The overlap question — when cost is the driver, which one? Open

This is the real discovery problem, and it is sharper than "two different problems."

The argument for the Data Store on pure cost grounds is overlap. Models share tables. Ten models all using orders, cached at model grain, is either ten copies of orders or a deduplication problem. Loaded once at table grain, it is one copy that ten models read.

If that holds: small scale favours Pulse for its simplicity; scale favours table loading for its efficiency — and the guidance almost writes itself. Start with Pulse, move to the Data Store when your cached models start overlapping.

Needs confirming first: does Pulse deduplicate a table shared by several cached models today, or store it once per model? The dashboard already splits storage into model caches and direct loads, so it has been thought about. That answer decides whether this argument is real or imagined.

Do we claim consolidation at all? Open

Cross-warehouse joining is a scatter problem, one level up from Fivetran's — the data is in warehouses, just in two of them.

The uncomfortable part: a customer with a data team consolidates upstream using tools they already own. Our only claim can be that we make it a click instead of a project. Worth deciding whether we make that claim, because it sets who this is for — which is stage 2.

Stage 2

Who is the user

The build assumes one answer. The rest of the product assumes another.

What the wizard implies

A data engineer

It asks for a watermark column, a primary key, a hand-written WHERE clause with runtime variables, retry counts, and pre/post-sync TQL. That is someone who runs pipelines for a living and knows the source table's internals.

What Pulse implies

A model owner

The whole interaction is "Cache Model." One decision, reversible, no knowledge of the source needed.

These sit one nav item apart in the same product, with wildly different assumed skill. The design currently implies one audience in two moods. The evidence says two audiences sharing a store.

One consequence either way Proposed

Even for a data engineer, the wizard asks for knowledge that usually lives with whoever owns the source system — which column is the real key, which one reliably updates. So the product should detect and propose rather than ask cold: suggest the primary key from source metadata, suggest watermark candidates by name and type, and let the user correct.

That single move makes the flow survivable for the model owner too, which may make the audience question less binary than it looks.

Needs answering Is this aimed at the data engineer only, or must a model owner be able to complete it unaided? Everything about the wizard's density follows from this one answer.
Output of stages 1 and 2

Scope and mental model

The thing everything downstream is derived from. Left unfilled on purpose — this is the decision, not a finding.

The mental model, once we can state it

One sentence the user would recognise as true — what they think is happening when they use this. Candidate to argue with: "I am bringing a copy of these warehouse tables into ThoughtSpot, and keeping it current, so I can analyse them here."

In scope — to be agreed Open

My reading of what must be in, given stage 1:

  • Pick a connection, pick tables, load them
  • A schedule — data that goes stale silently is worse than no data
  • Incremental load; without it, frequent refresh of a large table is unaffordable, which makes the schedule a lie
  • Visible health: last sync, status, and what to do when it failed
  • An answer for failure, deletion and access — not polish. Nothing here falls back to live, so without these the product is unsafe

Out of scope — candidates, each with its reason Open

  • Pre/post-sync TQL. Its four real uses are: recompute a derived table, clear a staging table, set permissions, run a quality check. Permissions and quality checks should be done properly in the product; derived tables belong in modeling. An escape hatch is an admission the product doesn't cover the case — and this one runs arbitrary SQL on a schedule inside our database, invisible to everyone but its author.
  • Schemas. A schema is simply a folder of tables. We have one database and the data workspace already organises objects; a second organising system is one more thing to maintain and reconcile. The one problem schemas genuinely solve for us is two connections both having a CUSTOMERS table — auto-qualifying by connection name is more legible than making people file things.
  • Custom SQL. Powerful, and it turns a query into a maintenance liability that breaks silently. Ask whether a model can do the same job later.
  • Column renaming and type editing at load. Border 2 — this is Data Studio's job. See the split below.

Where each decision belongs

Renaming, types, which columns matter, keys — modeling does all four. So the question is not whether the loader can do them, but where they should live.

Must be load time

Physical

  • Which columns come across
  • The primary key, for syncing
  • The watermark column
  • Schedule and frequency

You cannot model a column you didn't copy.

Better at model time

Semantic

  • Display names
  • Business definitions
  • How a column is used
  • Joins and relationships

Meaning changes often; changing it shouldn't mean re-loading.

Contested

Type

  • Physical — how bytes are stored
  • Semantic — what you can chart

Recommendation below.

Type — my recommendation Proposed

Warehouses don't share a type system: Snowflake's NUMBER(38,0), BigQuery's INT64, Postgres's numeric all have to become something here. That conversion happens at load whether or not we expose it.

But what a user cares about is not storage, it is what they can do with the column — sum it, put it on a date axis, use it as a label. Convert sensibly at load and don't ask. Expose the question in modeling, phrased as behaviour — a date · a number you can add up · a label — not as database types.

Same logic for renaming: the load layer stays close to the source; the model layer is where naming for humans happens. If renaming at load survives anyway, the source path must always be shown beside it.

Stage 4

Positioning — where it sits, and why there

Two live options, and they aren't cosmetic: they say different things about what this is.

What the build does now

Two nav items

AgentDB Store and AgentDB Pulse sit side by side in the left nav.

Says: these are two products that happen to share a name. The customer must know which they need before clicking.

An earlier iteration in the same folder

One item, tabbed

A single Agent DB with Tables · Models · Connections · Jobs inside it.

Says: one store, and what's in it arrived two ways. Matches the storage meter that already splits model caches from direct loads.

Which I'd argue for Proposed

One store as the destination, with the two ways in living where the work is. The customer should never stand at a fork choosing between two products — the surface they're on should choose for them.

Caching a model is a decision you make while looking at a model, so it belongs on the model. Loading tables is a decision you make while looking at a connection, so it belongs there. What they share is the destination: one place that answers "what is in my store, how full is it, and is it healthy."

But this only works if the connection question is settled — because today the store needs its own new connection, which forces the choice upstream, before the user has any evidence they need it. See the open question below.

Needs answering Why must the connection be new rather than reusing an existing one — technical constraint or product decision, and can it change? If it must stay, the hardest design problem in this product is helping someone choose correctly at the moment they know least.
Needs answering Naming. The build says Agent DB is the product and Pulse is a feature inside it. The shipped Pulse prototype says Pulse is the product and AgentDB is the store underneath. Both are shipping-adjacent. This needs a person to settle it.
Stage 5

The workflow

Capabilities here are derived from scope, not inherited from the acquired product. What follows is what exists today, so we can decide what survives.

Step 1 — what data connection → sync a table, or the result of custom SQL → pick tables (multi-select) Step 2 — what shape where it lands (schema, target table name) per column: does it come across · what is it called · what type · is it the key Step 3 — how often, and how safely repeat · start time · days incremental load: watermark column, comparison, WHERE clause alerts on failure · pre/post-sync TQL · retry policy

What scope does to this Proposed

If the boundaries in stage 1 hold, step 2 nearly disappears. No schema, no renaming, no type editing — leaving only which columns come across and which is the key, both of which can be proposed rather than asked. Step 3 loses TQL. Step 1 loses custom SQL.

What remains: pick tables · confirm what we detected · set a schedule. That is a flow a model owner could finish, which loops back to stage 2.

How incremental load actually works

Two different columns doing two different jobs — the part most easily conflated:

  • The watermark answers which rows do I fetch? A column whose value only goes up, usually updated_at. Each run asks for rows changed since last time.
  • The primary key answers what do I do with each row I fetched? If that key is already in our copy, overwrite it; if not, add it. "Upsert" is just update + insert.

Watermark is what to pull. Primary key is where to put it. An orders sync at 6am pulls the 4,000 rows changed since yesterday — some new orders, some old ones whose status changed — and merges each by order_id, without re-pulling 500 million rows.

Bulk, or one table at a time

The build does both, awkwardly. Step 1 multi-selects with a select-all and a "3 of 46 selected" counter. Step 2 then makes you configure columns per table — so it invites you to pick twenty tables and punishes you with twenty mapping screens.

The fix follows from scope: if mapping shrinks to detected defaults, bulk becomes genuinely fast and per-table configuration becomes an exception you open only when something looks wrong. Open

Stage 6

After the run — what the user is shown

Also derived from scope: you show what the scope made possible to get wrong.

The build has a Jobs view, a table detail page with sync history — last sync time, who ran it, rows retrieved, time taken, status — and email alerts on failure. That is a reasonable start and covers the happy path.

What it does not cover, and this is the serious gap Trap

A sync has been failing for three days. The table still exists. It still answers questions — with three-day-old data, and no fallback to live. Someone is looking at stale numbers believing they are current.

Pulse had a version of this and could afford to be quiet about it, because a stale cache falls back to querying live. Here there is nothing to fall back to. Whatever we show has to reach the consumer of the data, not just the person who set up the sync — which is stage 7.

Needs answering What does a model built on a failing table show its viewer? This is the same question your parked Pulse freshness work was answering, and the answer there may transfer.

Capacity becomes an active constraint Open

Raw loaded tables will dwarf model caches — the build already shows 0.47 TB of direct loads against 0.84 TB of model caches, and that is with sample data. Pulse's usage meter stops being a display and becomes something that blocks work.

What happens at the limit? Who is warned, at what threshold, and what gets evicted?

Stage 7

Consumers — where the tables surface, and how they get used

The stage the current build stops short of entirely, and the one where duplicating Data Studio is most likely.

Nothing in the nine screens shows a loaded table becoming anything. It arrives in the store and the story ends. But the tables also get an entry in the data workspace, and the entire point is that someone models on them.

Needs answering In the data workspace, does the Source column read agentdb for a loaded table, or the original warehouse? Reading agentdb is honest about where the query lands but loses provenance; reading Snowflake keeps provenance but hides that it is a copy. Pulse solved the equivalent problem with an indicator on the model name rather than by changing Source — which may be the precedent to follow.

Three levels, not two

Your question about deleting exposed something structural: the build treats as one object what is really three. Separating them says what each feature attaches to, and what cascades into what.

Level 1

Connection

  • Credentials, account, role
  • Warehouse type
  • What tables are reachable
  • Test · edit · delete

Deleting cascades into everything below. Largest blast radius in the product.

Level 2

Sync

  • Which tables, which columns
  • Primary key, watermark
  • Schedule, incremental settings
  • Alerts, retries
  • Run now · pause · edit

The pipeline. Configuration, not data.

Level 3

Table

  • The loaded rows themselves
  • Size, row count, last refresh
  • Appears in the data workspace
  • Things get built on it

The data. What models, answers and liveboards depend on.

Which answers your delete question Proposed

"When you delete a table, do you want to stop its future caching too?" — it depends which object is being acted on, and each combination is something someone wants:

  • Delete the data, keep the sync → the next run refills it
  • Keep the data, stop the sync → it goes stale but stays usable. This is pause
  • Delete both → gone entirely

Pulse already solved this vocabulary — purge deletes the snapshot and keeps the settings; disable stops the caching and keeps everything. Already reasoned through, already agreed with the team. It should transfer rather than be re-invented.

But deletion is not the same act in the two products Trap

In Pulse, purge is safe — the model falls back to live and nothing breaks. In the Data Store there is no live to fall back to. The copy in AgentDB is the only copy ThoughtSpot has. Delete it and every model, answer and liveboard built on it breaks.

Same word, same button, completely different consequence. Sharper still because loaded tables appear in the data workspace, so people will build on them without knowing how they got there.

Permissions and access — the consequence of copying

With a live connection, the warehouse enforces access. The query runs as someone, and if they can't see a table in Snowflake, Snowflake refuses. ThoughtSpot never has to decide.

Copy the data and the warehouse is out of the loop — ThoughtSpot becomes the only thing between a user and that data. So copying can silently widen who can see it. Row-level security and column masking cease to exist on the copy.

This is the question an enterprise security review asks first. The acquired product answers it with a Share button and permission grants hand-written into post-sync TQL.

What has to be decided Open

  • Does a loaded table inherit anything from its source, or start with fresh ThoughtSpot permissions?
  • Who may create a store connection, and who may load tables? Admin-only, or delegated?
  • Row-level security — if the warehouse filters rows per user, that filtering is gone the instant we copy. Refuse to load such tables, reproduce the rules, or accept the gap knowingly?
  • Column masking — same problem, same three options.
  • Who owns a loaded table, and who may delete it given the blast radius above?

Pulse has a smaller version of this and it never surfaced, because a cached model is the same model with the same permissions — the cache is invisible and creates no new object. Here we create new objects people can find, share and build on.

Running alongside

The evidence we should go and get

Most of this is decidable by gut. This part isn't, and it is obtainable.

Who uses the current data store product, and how Open

The strongest available evidence, and nobody has looked at it. The acquired product has real customers doing real things. Specifically worth knowing:

  • How many tables does a typical customer load, and how often do they refresh?
  • Do they use incremental, or full reload?
  • Does anyone actually use custom SQL, pre/post-sync TQL, column renaming, type editing? Each answer either justifies a feature or lets us cut it.
  • Do loaded tables get modelled on, or loaded and forgotten?
  • Who are the users by role — engineers, analysts, admins?
  • What do they contact support about? That is the trap list, written by reality.

Questions for the PM

  1. Is the Data Store a separate SKU, an entitlement, or on for everyone?
  2. Is the target user the data engineer only, or must a model owner complete it unaided?
  3. Why must the connection be new rather than reusing an existing one — and can that change?
  4. What happens to source permissions, row-level security and column masking on a loaded table? A blocker, not a detail — it is what a security review asks first.
  5. Does Pulse deduplicate a table shared by several cached models, or store it per model?
  6. Is cross-warehouse joining the headline reason to build this, or is it cost and speed?
  7. Which acquired features have real usage behind them, and which merely shipped?
  8. Full reload as a safety net against what incremental misses — acceptable, or too expensive?
  9. Does a loaded table show agentdb as its Source in the data workspace?
  10. Where is the boundary between the loader and Data Studio's cleaning?
Appendix

The traps

Cross-cutting, so they sit here rather than in one stage. Every one fails quietly — the product keeps working and the numbers are wrong. For analytics that is the worst failure mode there is.

TrapWhat happensWhat we need to decide
Silent updates Trap A row changes at source without updated_at being touched. The watermark never sees it, so our copy keeps the old values. No error. Require a trustworthy watermark, warn about the limitation, or schedule a periodic full reload to self-heal?
Deleted rows Trap A row is deleted at source. Deletion produces no new watermark value, so incremental can never see it. Our copy keeps a row that no longer exists — counts and totals permanently wrong. Same question, sharper. Full reload is currently the only honest answer. How often, and who decides?
No usable key Trap The table has no primary key, or the user picks a column that isn't unique. Merging then duplicates rows or overwrites the wrong ones. Detect and propose the key. Block incremental when uniqueness can't be verified?
Schema drift — added Source gains a column. Our mapping doesn't know about it, so it never arrives. Follow the source automatically, or require someone to opt in?
Schema drift — removed Trap Source loses a column the mapping expects. The sync fails — or worse, succeeds without it and every model using it breaks downstream. Fail loudly or continue? Who is told, and what does a model built on it show?
Schema drift — retyped A column's type changes at source and no longer fits the target. Fail, coerce, or re-create? Ties directly to whether we let users set types at all.
Failing sync Trap Failing for three days. The table still answers questions with stale data and no fallback to live. Someone believes the numbers are current. What does a model built on it show its viewer? See stage 6.
Delete blast radius Trap Deleting a loaded table breaks everything built on it, with no fallback. Show dependents first, block, or warn? See stage 7.
Connection delete Deleting a connection cascades through every sync and table under it. Same question one level up, much larger radius.
Access widening Trap Live, the warehouse refuses users who shouldn't see a table. Copied, ThoughtSpot decides — so the data becomes visible to people the source would have blocked, with nothing saying so. Inherit source permissions, apply fresh ThoughtSpot ones, or refuse to load restricted tables?
Row filters lost Trap Source applies row-level security so each user sees only their region. The copy has no such rules — everyone sees everything. Detect and refuse, reproduce, or accept knowingly? Silence is not an option.
Two names Renamed at load and again in the model. Neither is authoritative and no number can be traced back to source. Settle where naming happens — see the load/model split.
Custom SQL rot The query references a column that later disappears. The sync breaks, and the logic lives nowhere anyone will look. Do we support custom SQL at all?
Name collision Two connections each have a CUSTOMERS table. Schemas, auto-qualify by connection, or force unique names?
Capacity Trap Raw tables dwarf model caches. The store fills and syncs start failing. What happens at the limit, who is warned, what gets evicted?
Invisible SQL Pre/post-sync TQL runs on a schedule inside our database, known only to its author. Cut it, or make it visible and auditable?
Bulk burden Twenty tables selected, twenty mapping screens. People abandon, or accept defaults blindly. Defaults good enough that mapping is an exception path.
