Baseline

  • The data store is AgentDB. Two products sit on it.
  • Pulse — cache a whole model, one click. Built and shipped.
  • Data Store — load individual tables on a schedule. The acquired interface.
  • Warehouse connectors only. No SaaS sources.
  • Needs its own new connection — an existing one can't be reused.
  • Loaded tables also appear in the data workspace.
  • Data Studio is being built separately, with modeling, testing and data cleaning.
00

Where it stands — 1 September

From the product thread. Several of my open questions have been answered; the entry-point question has become the live argument.

Settled since this doc was written

  • Schemas are dropped. One database per customer, db_[customer_name]; per-schema mapping is gone. Matches the cut we proposed.
  • Single-table selection, column subsets allowed. Multi-table selection is deliberately out — it is a real UI problem for column mapping. That answers the bulk-versus-one question: one at a time, on purpose.
  • Simple by default, advanced controls collapsed behind an edit action. Matches "detect and propose, mapping as the exception path".
  • AgentDB gets its own loose connection, separate from Embrace, because it copies rather than reads. Connections start blank — whoever creates one is usually not the person doing the modelling.
  • Synced tables surface in the normal tables and search sections, and models are built on AgentDB like any other source. That closes the "what does the table become" gap.
  • Two doors, two personas, deliberately asymmetric. Model caching is the analyst's, done from the model's Caching tab; extracts are the data engineer's, done from the store landing. The analyst may never see the store — which means unification is an architecture and billing decision, not a demand that both personas learn one product. It also licenses the store landing to carry data-engineer density.
  • The store holds tables — always. How they arrived is metadata, not identity.
  • Grouped by what created them: model or extract. Both are the unit someone acted on. Connection is a filter, not a group — there are only ever a handful, so grouping by connection yields a few enormous groups. This also matches what shipped: Pulse's dashboard lists models, not their constituent tables.
  • No migration path for existing Data Studio customers. Workarounds stay options, not commitments.

Pinned — decide these and the design follows

Pinned 1 · one entry point or two

For two: separate Doris instances · pricing limits diverge · a merged UI would imply cached and ETL'd data can be combined in one model, which they can't · joins across them would be unpredictable even on one instance, since cached tables are time-sliced and ETL'd tables are full · different personas · different connection models · limited overlap in practice.

For one: customers don't care about instances · pricing can be handled by showing and hiding · don't put complexity on customers or invent names that confuse them · AgentDB is a caching and storing layer, use one or both — and on that view Pulse becomes invisible entirely.

Built as two nav items today — option 2 of the four. Everything above the workflow depends on how this lands.

Pinned 2 · can a customer even have both?

Feature flags are proposed to enforce that a customer can't have Store and Pulse enabled at once. If that holds, no customer ever sees both — and the stakeholder ask to design a home page for the two together has no user. Contested: the objection is that separate instances shouldn't be assumed, and noisy-neighbour worries could be handled with compute groups instead.

Pinned 3 · shared or independent storage

If Model cache and AgentDB share storage, one capacity meter and the table-overlap argument both hold. If independent, they are two separate meters and two separate limits, and the "start with Pulse, move to Store when models overlap" guidance falls away.

Pinned 4 · direct JDBC access

"Customers never log into AgentDB directly" is disputed — the counter-position is that AgentDB must stand on its own and customers should connect over JDBC. This changes what the product is. If customers connect directly, AgentDB is a database they operate, not an internal store we manage — and the access questions in item 07 get considerably sharper, because we would be handing out credentials to copied data.

Pinned 5 · who manages the data store?

Storage is one shared pool, but the two personas enter through different doors. The analyst caches a model from its Caching tab and never visits the store — no capacity meter, no sense there is a container at all. The data engineer lives on the store landing.

So when an extract fails for want of space, the cause was created by someone who can't see the pool and gets no signal. Separate products can't have this problem — each has its own quota. Unified storage inherits a shared resource with no shared accountability.

Needs an owner, and probably one of: cost shown to the analyst at the moment they cache, a quota per persona, or a named owner for the pool. Not a detail — it is the strongest argument against unification, and it isn't the join problem everyone has been arguing about.

Also open, less design-facing

  • Default sync schedule — daily versus no default. Leaning daily; the worry is users not noticing a default and syncing continuously.
  • Incremental can't be a pure default — it needs key columns and watermarks from the user. Confirms the trap; an API path for enterprises is worth scoping.
  • Query resource limits, pricing tiers (exposure around TB-scale fact tables), and timelines — 26.10 / 26.11 called unrealistic against current bandwidth.

What it is, and what it isn't

One sentence we all repeat the same way. Three borders we agree not to cross.

Starting point

Not a general ETL tool. A loading step for analysis.

Three borders

BorderProposed line
FivetranThey consolidate scattered sources into a warehouse. We move data out of one into ThoughtSpot. Scattered source data isn't our problem.
Data StudioLoader does fidelity — data arrives intact. Data Studio does shape and meaning.
PulseUnsettled. Both cut cost. Only this one enables cross-warehouse analysis.

Questions

  • PMIs cross-warehouse joining the headline reason, or is it cost and speed?
  • PMDo we claim consolidation at all, when a customer with a data team does it upstream?
  • EngDoes Pulse deduplicate a table shared by several cached models, or store it per model? If ten models sharing one table means ten copies, table loading is cheaper at scale — and that becomes the guidance.
  • PMEngWhere exactly is the border with Data Studio's cleaning?

Who is the user

Name one primary user. The interface's density follows from it.

  • The build assumes a data engineer — watermark column, primary key, a hand-written WHERE clause, retry counts, pre/post-sync TQL.
  • Pulse assumes a model owner — the whole interaction is "Cache Model".
  • They sit one nav item apart, in the same product.

Questions

  • PMData engineer only, or must a model owner complete it unaided?
  • EngCan we detect and propose the primary key and watermark from source metadata? The wizard asks for knowledge that usually sits with whoever owns the source system, not the person clicking through.
  • PMWho is buying this — the team that owns models, or a different one?

Scope and mental model

The output of 1 and 2. If we leave with only this, the session worked.

Mental model — agree one sentence

To argue with: "I'm bringing a copy of these warehouse tables into ThoughtSpot and keeping it current, so I can analyse them here."

Proposed in scope

  • Pick a connection, pick tables, load them
  • A schedule
  • Incremental load — without it, frequent refresh of a large table is unaffordable
  • Visible health: last sync, status, what to do when it failed
  • An answer for failure, deletion and access — nothing here falls back to live

Proposed cuts

FeatureReason
Pre / post-sync TQLArbitrary SQL on a schedule, visible to nobody. Its real uses belong in the product or in modeling.
SchemasA folder of tables. The data workspace already organises objects.
Custom SQLA query that breaks silently, with logic nobody will find.
Renaming and types at loadData Studio's job. Two names means no traceable number.

Questions

  • PMEngDo the four cuts survive? If they all go, wizard step 2 almost disappears.
  • EngWhich of them does the current customer base actually use?

Positioning

Agree the shape in the nav. Settle the naming.

  • Build today: two nav items — AgentDB Store, AgentDB Pulse. Says two products sharing a name.
  • Earlier iteration: one item with tabs. Says one store, filled two ways.
Biggest concern

The Data Store needs its own new connection. That forces the choice to connection-creation time — before tables, before a model, before any evidence it's needed. And a customer on Snowflake who wants both ends up with two connections to the same warehouse.

Questions

  • EngRiskWhy must the connection be new — technical constraint or product decision? Can it change?
  • EngCan a live connection be converted later, or is it recreate-from-scratch?
  • PMNaming. The build says Agent DB is the product and Pulse a feature. The Pulse prototype says the opposite.
05

Workflow

Capabilities derived from scope, not inherited. Walk the steps, mark what survives.

StepToday
1 · SourceConnection → a table or custom SQL → multi-select tables
2 · Map columnsTarget schema and name; per column — comes across, name, type, key
3 · ScheduleRepeat, days; incremental with watermark and WHERE clause; alerts; pre/post-sync TQL; retries

If the cuts hold, this collapses to pick tables → confirm what we detected → set a schedule.

Questions

  • EngIs incremental load available on every warehouse we support?
  • EngIs change data capture an option, or are watermarks the only mechanism? CDC reads the transaction log, so it catches deletes and updates that don't touch a timestamp — both of which watermarks miss silently.
  • EngCan we run a periodic full reload as a safety net, and what does it cost?
  • DesignBulk versus one at a time — step 1 invites twenty tables, step 2 makes you configure twenty.
06

After the run

Agree what health looks like, and who is told when it isn't.

The build covers the happy path — Jobs view, sync history, email alerts on failure.

The gap

A sync failing for three days. The table still answers questions, with stale data and no fallback to live. Pulse could be quiet about this because a stale cache falls back. Here there's nothing to fall back to.

Questions

  • PMRiskWhat does a model built on a failing table show its viewer? The parked Pulse freshness work was answering this — it may transfer.
  • EngWhat's the storage limit, and what happens at it — syncs fail, or something gets evicted?
  • PMWho is accountable for a failing sync? That decides who we notify.
07

Consumers

How loaded tables appear downstream. Confirm we're not rebuilding Data Studio.

Nothing in the nine screens shows a loaded table becoming anything. It arrives, and the story ends.

Three levels, not one

LevelHoldsDeleting it
ConnectionCredentials, what's reachableCascades through every sync and table beneath it
SyncTables, columns, key, scheduleStops refreshes. Data stays and goes stale — this is pause
TableThe loaded rowsBreaks every model, answer and liveboard on it

Pulse already has this vocabulary — purge keeps settings, disable keeps everything. It should transfer. But in Pulse purge is safe, because the model falls back to live.

Treat as a blocker

Live, the warehouse enforces access — Snowflake refuses anyone who shouldn't see a table. Copy the data and ThoughtSpot becomes the only thing in the way, so copying can silently widen who can see it. Row-level security and column masking don't survive the copy.

Questions

  • EngRiskWhat happens to source permissions, row-level security and column masking on a loaded table? Inherit from source, apply fresh ThoughtSpot permissions, or refuse to load restricted tables. Silence isn't an option.
  • PMWho may create a store connection, and who may load tables?
  • PMDesignIn the data workspace, does Source read agentdb or the original warehouse?
  • PMDoes deletion show dependents first — blocked, or allowed with a warning?
08

Evidence to get

The only part that can't be settled by judgement. Commission it before we design.

Who uses the current data store product, and how? Real customers, real usage, nobody has looked.

  • How many tables loaded, how often refreshed?
  • Incremental or full reload?
  • Does anyone use custom SQL, TQL hooks, renaming, type editing?
  • Do loaded tables get modelled on, or forgotten?
  • Users by role — engineers, analysts, admins?
  • What do they contact support about?

Question

  • PMWho can get this, and by when?
