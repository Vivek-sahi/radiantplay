1. The frame

What we are building. The console for AgentDB: the web app a customer uses to load data into their own analytics database and read it from any tool. The database is Apache Doris. The console is ours. It ships in December as a standalone product with its own sign-in, sold alongside ThoughtSpot and usable without it.

Who it is for. Three people and a crowd of tools.

PersonaRoleComes to the console toHow often
The platform ownerAdminSet the account up: people, identities, the ThoughtSpot connection. Then keep it safe.Week one daily, then monthly
The data engineerEditorCreate tables, set up loads, check they landed, find out why not, change things.Many times a day
The analyst or developerViewerSee what is there, run a read, test a query before an app or agent uses it.Weekly
ToolsQuery or Ingest identityThoughtSpot, other BI tools, apps and agents read. Pipelines load. They never see the console.Constantly

What success looks like. First session: a new customer creates a table, loads a file into it and sees it in ThoughtSpot without asking anyone. Every day after: the data engineer can tell in under a minute whether last night's load landed, and if not, why. December: engineering ships the console from this document and the prototype without a design question they cannot answer from them.

Principles. Five. Each has a consequence a screen can be checked against.

  1. Show only what the database knows. No tool names, no schedules, no forecasts. If Doris cannot tell us, the console does not say it.
  2. SQL has one home. The editor creates, changes and queries. No forms and no Create buttons in December. Empty states point to the editor.
  3. Organise by job, end in something to copy. Connect is a set of clients, not a list of facts. The last element of every block is copyable.
  4. Type every identity by its door. Query or Ingest. Nothing is an "app" or a "pipeline" to the database, so nothing is to us.
  5. Borrow the standard, invent nothing. Databricks for the catalog, VeloDB for the editor, ClickHouse Cloud for Connect. An engineer who has used one database console needs no explanation.

2. What AgentDB is

AgentDB is a database that ThoughtSpot sells on its own. It runs on Apache Doris, an open-source analytics database. A customer gets one AgentDB of their own. Inside it they can have several databases, and each database holds tables directly, with no folders in between. They push data in with their pipeline tools, and read it from anything: ThoughtSpot, another BI tool, an app, or an AI agent. ThoughtSpot is one client among many.

The console is the web app we are designing. It is not the database. It is the window onto the database: it shows what is in there, lets people create tables and keys, and shows what the database has been doing.

Everything else on this page follows from one fact: the console can only show what the database knows. It knows which account did what, to which table, and how long it took. It does not know what tool was behind the account, or why.

3. The two doors

Doris has two separate ways in, on two different ports. A port is a numbered entrance on a server. Each entrance speaks one language.

The load door speaks HTTP, the language of the web. A tool sends a whole file of rows to a web address that names the database and the table. Doris takes the file in. This is called a stream load. It is the only way to get data into AgentDB in volume.

The query door speaks the MySQL protocol. Any tool that can talk to a MySQL database can talk to AgentDB the same way: it sends SQL, it gets rows back. This is how every reader connects. The word MySQL belongs on this side of the product only. It has nothing to do with loading.

Evidence · Dmitrii, then Harviish

"No ingestion via MySQL. HTTP only." The prototype's Pipelines block told ETL tools to treat AgentDB as a MySQL destination. That was a misreading of the PM's "MySQL" item, which only meant tools can query us like MySQL.

4. Who connects, and how

Three kinds of identity appear in the PM's list. People sign in to the console. Service accounts are users too, in Doris's sense: a username and password a tool signs in with. They live under Access. API keys get a page of their own. Whether a key and a service account are one thing with two names, or two things, one for each door, is the one question the list leaves open; see the open questions.

Either way, a tool's identity is typed by the door it uses: Query or Ingest. Scoping an identity to particular databases or tables is not December.

5. Signing in

The console has its own sign-in. There is no ThoughtSpot sign-in and no single sign-on for December. The PM's flow, as told on 14 Oct:

  1. Enter your emailThe address an Admin invited, or the one ThoughtSpot set up the account with.
  2. Receive a codeA one-time login code arrives by email. Enter it. This proves the address is yours.
  3. Create a passwordFirst time only. Rules shown inline, not after a failed attempt.
  4. You are inLater sign-ins: email and password. The code step returns when something looks new, such as a new device.

The reason is SOC 2, the security standard enterprise buyers ask for. SOC 2 is an audit of controls, not a list of features, but a handful of its controls are visible in a console and should be designed in from the start rather than bolted on.

Visible in the console
  • Invitation, not self-signup. Only an Admin adds a person. The first Admin is set up when ThoughtSpot provisions the account.
  • A second factor for Admins, at least. The email code can serve as it for December; an authenticator app later.
  • Sessions end. Idle sessions time out. Sensitive actions, such as creating a key or changing a role, ask for the password again.
  • Lockout after repeated failed attempts, with a plain message.
  • An audit trail of admin actions. Who created or revoked a key, who changed a role, who deleted a table, when. Auditors ask for this first. Not in the December list; a section under Access, later.
  • Least privilege by default. A new person is a Viewer until someone raises them. Keys are scoped to tables, not to everything.
  • Secrets shown once. A key's secret appears at creation and never again. Rotate replaces it.
  • Keys can expire, and "last used" shows the stale ones. Removing a person flags the keys they created for review.
  • Access review. The people list shows last active, so an Admin can review it quarterly.
Not visible, engineering's
  • Encryption in transit on both doors. The load address should be https, not http as in the curl sample.
  • Encryption at rest, backups, restore, disaster recovery.
  • Change management, vulnerability scanning, vendor reviews, incident response.
  • Customer data deletion when a contract ends.
To confirm with Harviish

Invitation only, or can anyone with the link sign up? The flow as told could be read either way. And is the first Admin created by ThoughtSpot, or by the customer?

6. Putting data in

A load is one file going into one table. Here is the whole sequence, and what the database records at the end of it.

  1. A table existsSomeone created it in the console, so Doris knows its columns and types.
  2. A tool sends a fileThe pipeline tool, or a script, sends a file to the table's load address, signed in as an Ingest key.
  3. Doris checks the keyCan this key load into this table? If not, the load is refused.
  4. Rows landThe rows are added to the table. Whether they replace what was there depends on the table and the tool.
  5. A receipt goes backTo the tool that sent the file: rows loaded, bytes, time taken, success or failure.

The recipe Dmitrii pasted, line by line

curl is a small command-line tool that sends a web request. His sample is the exact command a pipeline engineer would run to push one file into one table. The console shows this on each table's own page and in Connect, filled in with the customer's host, the database, the table and the identity, with the header set explained, so nobody has to work it out.

"Doris has no idea who is pushing data to it, so there is no source differentiation." The Overview chart "Storage by source" and the Source column on Data were built on tool names. Both go.

Asked of engineering · Harviish, 14 Oct

Doris exposes per-query latency, status, error and scanned bytes through the audit log, and per-load rows and bytes through stream-load records. Are both enabled in our setup, and what is the retention? Until the answer, the console promises only the certain tier.

Sync modes

A sync mode is how a pipeline tool keeps the copy in AgentDB in step with the source system.

  • Full refresh wipes the table and reloads everything, every run. Simple, slow for big tables.
  • Incremental sends only rows that are new or changed since last time.
  • CDC, change data capture, replays every single insert, update and delete from the source as it happens.

The prototype claimed "full refresh only". Dmitrii says which modes AgentDB will support is still to be confirmed. Until then the console should not name any.

When a load goes wrong

Added on 14 Oct, and confirmed by Harviish the same day: users will use the SQL editor to query, verify and debug what has loaded. Loads fail in ordinary ways: a retry loads the same file twice, a timeout loads half of it, rows that do not fit a column type are dropped silently and counted as filtered, a comma inside a value shifts a row's columns, last week's export is sent again, a full refresh empties the table and the new load fails. The analyst sees a wrong number in ThoughtSpot and messages the data engineer. The pipeline tool says "run succeeded". The table is the only place that shows what actually landed, and the engineer checks it with two or three queries: rows per day, duplicate IDs, latest date, empty amounts.

7. What is inside

Where a database lives (Vivek, 19 Oct). AgentDB runs as clusters. A cluster holds many databases. Each customer is given one or more databases on a cluster, and the allocation is done by us, in the backend. A customer never creates, moves or deletes a database; the console shows the ones they have, and nothing above them. Customers never see the cluster, nor each other.

The catalog is the list of everything in the database. A customer's AgentDB holds one or more databases, and each database holds three kinds of thing directly, with no folders.

  • Tables hold rows. Data is loaded into them.
  • Views are saved queries that behave like a table but store nothing. Each time you read a view, its query runs again on the tables underneath.
  • Materialised views are saved queries that store their result, and refresh it later. Fast to read, but they take storage.

Every database console shows the catalog the same way, which is Damian's point: a tree on the left, the chosen object on the right with its columns, a sample of its rows, and its definition. Harviish picked the Databricks version as the reference. The catalog is Doris's own metadata, tables, views, materialised views, columns, the SQL that created each, and statistics, so it works with no source information at all. Databricks lists tables and views together under a schema with a kind icon, and gives each object tabs: Overview, Sample data, Details, History, Permissions, Lineage. For December we take Columns, Sample data, Details and History. Permissions and Lineage come later.

How things get created

SQL has two families of commands. One family reads and writes rows: SELECT, INSERT. The other creates and changes the shape of things: CREATE TABLE, ALTER TABLE, DROP TABLE, CREATE VIEW, CREATE MATERIALIZED VIEW. The second family is called DDL, data definition language. Doris accepts all of it as typed text.

For our product, DDL means every action that changes the catalog: create a database or a table, add or widen a column, delete, empty, create a view. The thread's rule is simple: every one of these must be possible as typed SQL, and forms exist only for the common ones. A table made by typed SQL looks identical in the catalog to one made by the form.

So creating is one path: the SQL editor. You go to SQL, write the statement for a table, a view or a materialised view, and run it. The object appears in the catalog. Changing things works the same way, through Open in SQL on an object's page. There is no form and no Create button. The empty state of Data says so and links to SQL. SQL is typed in exactly one place, and that place also runs queries, with the results table below.

Roles are enforced by the backend, not by hiding statements: a Viewer who runs a create gets a refusal from the server, and the console shows it in plain words. A link to the documentation sits beside the editor. Starter statements that pre-fill the editor can come later; the December editor opens empty.

8. Reading data

Every read is a query: a line of SQL sent through the query door by a key or a person. ThoughtSpot, another BI tool, an app, an agent, and the console's own editor all do exactly this. Doris keeps a record of each one in its audit log.

A query that is still running can be stopped. Doris does this by query ID, so the console shows the ID in the query's detail and offers Stop beside each running one.

Harviish wants queries and loads under one nav item, because both are activity logs on the same objects with the same filters. Vivek ruled the shape: one page called Queries, one list of every type, read, write and load, told apart by a Type column and filter. Columns: time, type, user, statement, tables, duration, size (scanned for a read, loaded for a load), status with the error, and Cancel on a running query by its ID. Whether load records exist in our setup, and for how long, is the open question to engineering.

Evidence · Dmitrii, Rahul, Harviish

Dmitrii: add a User column and filter. We removed "Run by" on 7 Oct; it comes back. Rahul: total queried size, latency and similar metrics, cancellation by ID, and ingest activity. Harviish: those are the Jobs page from the December list, and a deeper flow for the next review round.

9. Who may do what

Doris thinks in three layers. A privilege is one permission on one thing, such as read the orders table, or load into the orders table. A role is a named bundle of privileges. A user is given roles. To Doris, people and service accounts are both users.

Harviish fixed the December scope: three roles, no custom roles, no per-object privileges. The privilege layer stays inside Doris and the console does not expose it. What each role can do, in his words:

RoleCanCannot
ViewerSee everything. Run reads in the SQL editor.Create or change anything. Cancel queries.
EditorEverything a Viewer can. Create and change tables, views and materialised views. Cancel queries. Create API keys.Add people or service accounts.
AdminEverything.Nothing.

Access holds two lists, because to Doris both are users:

People

  • Add a person with a role
  • Change a person's role
  • Remove a person
  • Reset their password

Service accounts

  • Create one, typed Query or Ingest
  • Reset its password
  • Revoke it, and restore it
  • See when it was last used

Later, not December: custom roles, table-level permissions, the audit trail from Signing in, and reviewing a person's keys when they are removed.

Evidence · Harviish's consolidated list, 14 Oct

"Record the full user management flow, CRUD of users. Three fixed roles only, no custom roles or per-object privileges for Dec. Service accounts move from Connect to Access (they're users)."

10. The console: information architecture

Sign-in first, then three workspace pages and three set-up pages. Data is the landing page: the homepage metrics sit above its browser, so there is no separate Overview. There is no account above the databases; the tree starts at them and lands on the first. Data is the catalog in the Databricks shape. There is no header: the sidebar carries the navigation and, at its foot, the signed-in person (Vivek, 15 Oct). SQL is a page of its own with the catalog tree beside it, as in Snowflake and VeloDB. Queries is one list of everything the database ran, of every type.

Three rules hold it together:

  • One page per thing the database knows. Objects live in Data, what happened in Queries. Nothing appears twice.
  • Identities live in Access, never in Connect. Connect uses them through pickers and ends every block in something to copy.
  • Connect is organised by client, not by component. ThoughtSpot is one BI tool among the others, with no special treatment.

11. Jobs to be done, per page

Every job a person does in the console, grouped by the page where it happens. Who is the role that mostly does it. How often is per customer, once the product is in daily use. Criticality says what breaks if the job cannot be done: critical blocks the core path or security, high blocks a day's work, medium slows it, low is a convenience.

The core path for a new customer, in order, is the set of critical jobs: sign in, create a table, create an Ingest identity, get the table's load address, load, verify the load landed, create a Query identity, connect ThoughtSpot. Everything in the first week is on this path. Everything after is upkeep.

Design system audit, 14 Oct

Everything in v3 is built from Radiant Play, checked file by file. What the audit found and fixed:

  • Components. Twenty-one Radiant components: Vertical, Horizontal, Typography, Button, Select, Table, Modal, ModalFooter, TextInput, TextArea, SearchInput, NoData, ActionMenu, ActionMenuItem, Icon, Tabs, Tree, ProgressBar, Link, Card, Avatar. Plus the prototype's own primitives from v1, all built on tokens: PageHeader, StatTile, Panel, KeyValue, CopyField, CodeBlock, StatusPill, FloatingToast. Raw HTML only for layout and wrappers: div, aside, main, nav, header, span, and code for monospace values. No inline styles.
  • Tokens. Colours only from the system palette, six of them. Fonts only the primary and mono families. Font size only the small token. Radius only medium. Spacing tokens one to eight. Typography variants: page-title, modal-title, content-label, content-label-subhead, body-normal, footnote, overline, headline-large. No hex, no rgb, no named fonts, no pixel sizes for type.
  • Layout sizes. The rail, search box, editor height, column widths and caps were pixel literals. They are now thirteen custom properties derived from spacing tokens, declared once, and table column widths come from one shared set of token expressions. The only literals left are one-pixel borders.
  • Icons. Nineteen, all from the Radiant registry: database, formula, list-view, cord, key, lock, grid-view, table, collection, play, pause, copy, more, plus, add-user, upload-data, documentation, checkmark-circle, exclamation-point-circle.
  • Copy. Sentence case throughout. Buttons are imperative verbs.

Known deviations, for engineering:

  • The password field masks its text with a CSS rule, because Radiant's TextInput has no password type. Radiant needs a password input.
  • The shared v1 files carry three pixel literals that predate v3: the status pill's line height, the toast's width, and the header height, nav width and mark size in the shell. v1 is frozen, so they stay until Radiant provides tokens for them.
  • Tree selection and hover colours are the component's own.

Design system audit, 15 Oct

Vivek's review found that the 14 Oct audit had checked tokens, not the look. Every value was a token, and the result still did not look like Radiant. Eight of his eight notes were fonts, sizes or a sidebar that was not the product's. What it found and what changed:

  • Fonts. Identifiers (users, keys, columns, connection facts) and commands rendered in the mono family through raw code elements, at a size that differed from the cells around them. The mono family is a token, so the token audit passed it, but no Radiant component renders text in it. Now text renders only through Typography or a component's own default. No code elements, no font family in the prototype's stylesheet. The one exception is the SQL editor, which keeps the mono family (Vivek, 15 Oct). The copyable commands and samples are Plain, in v3's own CopyField and CodeBlock.
  • Tables. The Table was Radiant's; the cell renderers were not. User, statement, tables and identifiers are now plain cell text at the Table's own size.
  • Sidebar. The nav was built from the tertiary Button, whose own rule paints its icon brand blue, with overrides on top. Now it is Radiant's AppSidebar in the light colourway of the product's sidebar: text-only items, section labels, blue on light blue when selected, the signed-in person at the foot with the account menu. No icons, no header.
  • Prototype controls. The version, workspace state and signed-in role left the header for one gear menu floating bottom-right, a Radiant ActionMenu with three labelled groups. On the sign-in screen too.

The rule the 14 Oct audit lacked. Text renders only through Typography or a Radiant component's default, never through a raw element or a font declaration in prototype CSS. Navigation only through the Radiant sidebar. And an audit compares the screen with the product, not the stylesheet with the token file.

Deviations added, for engineering:

  • AppSidebar ships in the dark colourway with a tab-switcher row. v3 passes it the light system palette through its own custom properties and hides the one-tab row. Radiant needs a light variant of AppSidebar and a way to omit the tabs.
  • v3 no longer uses the v1 shell, so its pixel literals no longer apply to v3.
  • The code block for commands and samples is a pre in the primary family, because Radiant has no code block.

Visual design principles, 15 Oct

Eight rules a screen can be checked against. None adds a feature. v4 is built to them; scope is closed, the look is open (Vivek, 15 Oct).

  1. Size follows urgency, not the data model. The loudest thing on a page is what the person came for. Numbers sit at text size unless the number is the page; the only big type is the page title.
  2. Three sizes above the fold. Page title at 24, the selected thing at 20, everything else at 14 with 12 for labels. The 32px headline is not used.
  3. One canvas, no cards. White page beside the grey sidebar. Sections are separated by whitespace and the Table's own header band. The only bordered region is the browser, because a tree and a pane need an edge between them.
  4. Colour means state, nothing else. Blue is selected or clickable. Red is failed. Green is completed. Everything else is grey or black. A quiet day looks quiet.
  5. Tables are the content. The Radiant Table sits directly on the page, compact, with plain strings in every cell at one size. The only marks inside a cell are the status pill and the blue name.
  6. One primary button per page, top right. Run, Create API key, Add person, Create service account. On Connect the primary is Copy on the thing to paste. Data and Queries have none.
  7. One rhythm. 32 at the page edge, 24 between sections, 16 inside a section, 8 between things that belong together. Spacing tokens only.
  8. One way to say each thing. One relative time format for freshness (Just now · 4 min ago · 3 h ago · Yesterday, 09:14 · 2 Sep) and absolute clock times in the log, because a log is a timeline. One size format. One typeface, Plain, with the SQL editor as the single exception. If the product's screen and ours differ in how a thing reads, ours is wrong, token or not.

Withdrawn from the first draft as scope, not design: a link from the metrics line into Queries, and a draggable split in SQL. Ruled out on review (Vivek, 15 Oct): a status sentence on the metrics line. The line carries figures only.

17. Glossary

Apache Doris
The open-source analytics database AgentDB runs on. Fast at reading large tables, built for many users querying at once.
Port
A numbered entrance on a server. Doris listens on 9030 for SQL and 8030 for loads.
HTTP
The language of the web. Browsers use it to fetch pages; tools use it to send files to the load door.
MySQL protocol
The language MySQL databases speak. Doris speaks it too, so any MySQL-compatible tool can query AgentDB.
Stream load
Doris's way of taking in a file: send it to a web address that names the database and table.
curl
A command-line tool that sends a web request. The quickest way to try a stream load by hand.
Ingestion
Getting data into the database. Same thing as loading.
Sync mode
How a pipeline tool keeps the copy in step with the source: full refresh, incremental, or CDC.
CDC
Change data capture. Replaying every insert, update and delete from the source as it happens.
SQL
The language for asking a database questions and telling it what to create.
DDL
The SQL commands that create or change the shape of things: create, alter, drop a table or view.
Query
One SQL statement sent to the database to read rows.
View
A saved query that behaves like a table but stores nothing.
Materialised view
A saved query that stores its result and refreshes it later.
Catalog
The list of everything in the database: databases, tables, views, materialised views, and their columns.
Schema
The shape of a table: its columns and their types. Also used loosely to mean the catalog.
Audit log
Doris's own record of every query: who, what, when, how long, how much data, and the outcome.
Audit trail
The console's record of admin actions: who created a key, changed a role, deleted a table. A SOC 2 expectation.
Query ID
The identifier Doris gives each query. Needed to stop a running one.
API key
A username and secret a tool uses to connect. v1 called it a service account.
Privilege
One permission on one object. The everyday two are Select, to read, and Load, to ingest.
Role
A named bundle of privileges, given to users.
Login code
A one-time code sent by email to prove the address is yours. Part of sign-in.
MFA
Multi-factor authentication. A second proof at sign-in, such as a code, on top of the password.
SOC 2
A security audit standard enterprise buyers ask vendors for. It audits controls such as access, change and incident handling.
MCP
Model Context Protocol. The standard way an AI agent plugs into a tool to list what is there and run queries.
Metadata
Data about the data: table names, column types, who created what, when it was last loaded.
