Search data on model — use-cases and workflows

For review · 21 Sep 2026 · the working list for wrapping the exploration. Nothing here is final until Vivek calls it.

Principles that run through every story

SpotterModel is a copilot for the entire journey. Every use-case below has two first-class paths: the user does it by hand, or asks SpotterModel to do it. Neither is a fallback for the other.
Users iterate by trying, not by planning. Finding the right table isn't a separate discovery step: the user adds a table, previews it, and swaps it for another if it's wrong. SpotterModel copilots the trying. The workflows below assume this loop everywhere.

The use-cases

1Add tables and columns into a model

The user builds the model's foundation by bringing in tables — choosing which columns come along as they do.

Hypothesis: users don't want empty tables, and practically never want all columns (loading everything is also computationally heavy). So adding is a two-step flow — pick the table, then pick its columns — with "select all" available for the user who does want everything.
Manual
Browse or search the source tables, add one, select its columns in the same flow. Wrong table? Preview it, remove it, try another.
SpotterModel
Suggests the right tables and columns for what the user is trying to build; the user accepts, trims, or redirects.
2View the data in the added columns

First and foremost the user just wants to see the rows. They may or may not query. They may want a data snapshot — average, total, median — to get a feel for what's in a column.

Manual
Open the preview; the spreadsheet shows the data across all added columns. Pull a snapshot of a column when curiosity strikes.
SpotterModel
Answers "what does this column look like" — summaries, distributions, oddities — without the user leaving the flow.
3Join tables

Two tables per join, done visually on the canvas; the join's configuration opens as a modal.

Manual
Draw the join on the canvas, configure keys and type in the modal.
SpotterModel
Proposes joins — which tables, which keys, what type — for the user to accept or adjust.
4Preview the joined data — and trust it

After joining, the user wants to see the joined rows. Trusting the join is part of this same story: the preview is where a row explosion, null keys, or a wrong cardinality should become visible — seeing the rows and believing the join are one act.

Manual
Click the join, preview its data, sanity-check what the join did to the rows.
SpotterModel
Flags what the user might miss — "this join doubled your row count", "12% of keys didn't match".
Ruling: join-trust folds into previewing, not a separate story.
5Query the joined tables

Beyond seeing rows: asking question-shaped things of the model — aggregates, group-bys, the answers end users will eventually want.

Manual
Build queries in the Query view against the joined model.
SpotterModel
Takes the question in natural language and runs it against the model.
6Add formulas
Manual
Create a calculated field; it becomes part of the model like any column.
SpotterModel
Writes the formula from a description of what it should compute.
7Add filters
Manual
Filter a column and save the filter to the model.
SpotterModel
Applies the filter the user describes — "only the last two years, only retail".
8Add parameters
Manual
Create a named value to reuse across formulas and filters.
SpotterModel
Suggests where a parameter would serve better than a hard-coded value, and creates it.
9Review the semantics

The model answers only as well as its semantics are curated: friendly column names, descriptions, synonyms, measure vs attribute, formats, AI context. This is what makes the model AI-ready rather than merely joined.

Manual
Work through the Semantics view — rename, describe, add synonyms and AI context column by column.
SpotterModel
Drafts descriptions and synonyms, flags columns with weak or missing semantics, and lets the user approve in bulk.
10Validate the model end-to-end

Before handing the model over, the user confirms it answers the questions their users will actually ask. Try representative questions, check the answers are right, trace a wrong number back to its cause, fix, retry. Query is the test bench; this is the exit criterion for the whole journey.

Manual
Run the questions that matter in Query; verify against known numbers.
SpotterModel
Generates the representative questions, runs them, and reports which ones the model handles poorly and why.
11View model contents

See everything the model holds in one place — tables, columns, joins, formulas, filters, parameters — and understand its shape at a glance.

Manual
Open the model's contents view and read it.
SpotterModel
Explains the model — "what's in here, what joins what, what would I use this for".
12Remove and modify what's there

Every add has a counterpart: remove or reconfigure tables, columns, joins, formulas, filters, parameters. The hard design lives in removal with dependents — deleting a column a formula uses, deleting a table that's joined. This is also how a user recovers from mistakes: undo is remove-and-modify, not a separate story.

Manual
Remove or edit any item; the model explains the consequences on dependents rather than silently breaking them.
SpotterModel
Does the removal or change on request, and narrates what else it touches.
Ruling: sits after "view model contents" in the journey. Undo folds in here.
13Save the model

The user keeps their work. What saving makes available, and to whom, is the open question below.

Manual
Save with a name and description.
SpotterModel
Suggests the name and description from what the model contains.

The model's life after day zero

Two candidate stories, currently in neither list:

Returning to an existing model. A user reopens a model next week — or opens one a teammate built — orients quickly, and makes a change without breaking what works. The prototype already seeds this (the "existing" welcome variant).

Save vs publish. Is saving the same as making the model live for Spotter users, or is there a separate publish step with access control? Settings already carries row-level security and join rules, which implies the question.
