Caching for multi-source modeling

Proposal · 2026-08-12

Problem

Problem statement

How do we let users explore data modeling in real time, when caching enough data can take minutes to hours?

You can't join tables across warehouses. Every table in a model must sit in one warehouse — ours or an external one — and caching is what moves them there. Agent DB cached after modeling, so latency was optional. Here caching blocks the join the user is making.

Solution

Cache a slice to keep exploring

Users cache a slice of data and continue exploring immediately. If they want full data and accept the latency, they can choose that instead.

Ways to slice — and why time period wins

LeverJoins surviveWhyUX implication
Time period
last N hours / days		 Yes Both tables share the predicate meaningfully — an order and its shipment both fall in the last 7 days. The slice is coherent, not arbitrary One dropdown per fact table + a reference date column Recommend
Rows No Arbitrary cut. The first 500 rows of two tables needn't share keys, so a join returns near-zero matches — silently, with no signal it's a caching artefact Fallback only, where no date column exists and the other side is cached full
GB No Resolves to an arbitrary row cut, so same silent join failure. But it's the unit users think in for cost Show as a readout of the chosen window, never as an input

Time period also wins on filters and formulas: a 7-day slice gives correct answers for 7 days. A row slice gives an answer for an arbitrary subset, which means nothing.

How users cache

1 · DROP A TABLE — no caching

Tables land on the canvas uncached. Preview queries the source live, so the user can explore and understand the data with no wait at all.

2 · DRAW A JOIN — caching required

The join is what needs co-located data, so this is the trigger. Each table is cached separately. For each, we need a time period and a reference date column. Default to a short window — 6 or 12 hours — so the first cache is fast and the choice isn't weighty.

ad_impressions — 22M rows Cache [ last 12 hours ▾ ] by [ impression_date ▾ ] ≈ 37K rows · 30 MB · est. 1 sec

Good to have: detect fact vs dimension, so dimensions cache in full (they're small) and only fact tables need a window and a date column. Signals below.

3 · WHILE CACHING — partial capability

Preview loads progressively. Formulas and filters can be created. Join and clean cannot — they need complete data.

4 · CACHED, SLICED — full capability except cleaning

Preview, join, formula and filter all work. Cleaning still needs the full table.

5 · TESTING — may need full data

A question inside the cached period answers correctly. A question outside it can't be answered, and the user gets the option to cache full.

Barring join during the fill removes the one real hazard of progressive caching — two partially-filled tables joining on arbitrary prefixes. Nothing that depends on completeness is available until the cache completes.

Which approach are we taking?

ApproachIn?Reasoning
Slice the data Yes Makes the cache fast enough that exploration continues. Time period as the lever
Progressive use during the fill Yes Complementary, not an alternative. Gated to preview / formula / filter so nothing depends on partial data
Cache at join, not on drop Yes Costs nothing — preview is live anyway — and the window is chosen when the user knows what they're building
Target the majority warehouse If supported Move only the outliers: 4-of-5 tables already in Snowflake means caching 1, not 5. Largest single win available
Background + notify No Only justified at 45-minute scale, and slicing should prevent reaching it. Needs a notification surface we don't have
Entity subset
N accounts + related rows		 No Best join integrity of any option and needs no date column, but requires the join graph and likely isn't supported. Listed for completeness

Detecting fact vs dimension

Caching happens before joins exist, so classification uses column statistics only:

SignalFactDimension
A column with distinct count ≈ row countabsentpresent (natural key)
ID-shaped columns with heavy repetitionpresentabsent
Row countlargesmall
Date columnevent dateaudit date, or none

First two are reliable without joins. Show the guess, let the user correct it once per table. Good-to-have, not required — the fallback is asking per table.

Who this affects

Short term vs long term

SegmentSizeImplication
Do multi-source modeling Unknown Structurally a minority — single-warehouse models need none of this — but it's the differentiating capability
Hit the severe band (200M+ rows) Unknown If small, most of this is premature and MVP should cache fully and defer slicing
Need cleaning Unknown Cleaning is phase 2, so "no cleaning on a sliced cache" is acceptable now. It becomes the main reason to cache full later
Will ask questions outside a short window Unknown Drives how often step 5 forces a full cache. If common, the short default is friction rather than help
Why this approach holds up both ways. Short term: slicing plus progressive use keeps exploration real-time while cleaning is out of scope. Long term: cleaning arrives in phase 2 and needs full data — and nothing here blocks that, because full caching is already the user's choice at step 2 and forced at step 5. We aren't building a slice-only architecture that has to be undone.
