# POC scope — surfaces, actions, and what's inherited
_2026-08-06. The scope definition for the POC cut (_`?v=poc`_). Written to be reviewed by product and engineering, and to be taken to the SpotterModel team as a feasibility list. Everything below is derived from the code as it stands, not from earlier docs._

* * *
## 1. What POC is for
POC is the cut that **product and engineering spec against**. Three audiences, three questions:

| Audience | The question they're answering |
| --- | --- |
| Product | Is this the right scope for the first release? |
| Engineering | Can this be built, and what does it decompose into? |
| The SpotterModel / backend team<br><br>and What exists in data modeling vs what will be built | Does what already exists support this?<br><br>Does this need to be built or is it available to plug? |

Vision is the long-term cut — prep transforms, code blocks, the fuller agentic surface. Demo is the stakeholder cut and is finished. **Neither is under review. POC is.**
### The test POC has to pass
> Nothing on screen claims to work when it doesn't.

Every control is either wired or removed — there is no third state.

## 3. Decision 1: POC needs one dataset. It currently has three.
This is the "data contradiction", and it's the single biggest problem with POC as a review artifact. **Three unrelated scenarios are live at once:**

| # | Scenario | Tables | Where it appears |
|---|---|---|---|
| A | **Campaign performance** (marketing) | `orders`, `campaigns`, `users` in `marketing_db` | What POC's own journey builds — `MOCK_PLAN_BASE`, `AgentPanel.tsx:287`, reaching the canvas via `MRD_MODEL_TABLES` (`index.tsx:92`) |
| B | **Customer health / NPS** | `dim_accounts`, `support_cases`, `call_metrics`, `customer_found_defects`, `pendo_nps_enriched`, `csm_account_mapping` | The data browser tree — `ModelCanvas.tsx:4210, 4228–4251, 4327` |
| C | **Renewal risk** | `accounts`, `contracts`, `arr_snapshot`, `billing_events`, `usage_events`, `feature_adoption`, `qbr_sentiment`, `jira_cs_tickets` | Demo's agent injects these directly; readiness findings and the Spotter answer are written against them |

So a reviewer walking POC builds a **marketing** model, then opens the data browser beside it and sees **customer-support** tables. Neither set is the one the readiness findings describe. In Demo this is invisible because the agent injects its own tables and nobody opens the browser. **In POC the browser is the primary way data reaches the canvas**, so it's the first thing a reviewer touches.

**Recommendation: standardise on C, renewal risk.** It's the most developed set — eight tables with real column definitions, readiness findings written against them, and a working Spotter answer. It's also what stakeholders have already seen, so the prototype stays coherent across cuts. That means:

- the browser tree lists the renewal-risk tables (replacing B)
  
- the from-scratch plan proposes a subset of them (repointing `MOCK_PLAN_BASE`)
  
- A and B stop appearing anywhere POC can reach
  

⚠️ `MOCK_PLAN_BASE` is also read by Vision's Workspace and by `SpotterXShell`, so repointing it is not a local edit. The cheaper move may be a POC-specific plan constant.

## 4. Decision 2: the agent is inherited — so what does POC own?
The agent comes from the SpotterModel work another team is doing, and is **reused entirely**. That makes POC's real contribution the **seam**, not the conversation. This is the section to take to that team.
### What the canvas exposes today
Three entry points, all in `ModelCanvas.tsx`, all currently driven by our own scripted agent:

| Call | What it does | Who calls it now |
|---|---|---|
| `agentAddTables` | Places one or more table cards on the canvas. Wraps `addToCanvas`, so an agent-added card is indistinguishable from a hand-added one. Batch adds pass `{ select: false }`. Returns a promise. | `AgentPanel`, Demo script |
| `agentAddJoins` | Draws committed joins, then runs the auto-layout | `AgentPanel`, Demo script |
| `agentAddPythonSource` | Adds a Python source card | `AgentPanel`, Demo script |

**This is the whole API surface between a conversation and the canvas.** If SpotterModel's agent can call these three things, it can drive POC's canvas. That's the feasibility question in one line.
### The open question
POC's conversation today is **our** generic from-scratch flow (clarify → plan → build), not SpotterModel's. So:

- **Is that flow a placeholder** for SpotterModel's agent, to be swapped at the seam?
  
- **Or is it POC scope** in its own right, with SpotterModel's agent arriving alongside it?
  

This changes what gets built. If it's a placeholder, POC should stop investing in the conversation and invest in the seam — the three calls above, plus whatever else the agent needs to read (canvas state, selection, schema). If it's scope, the clarify→plan→build flow needs specifying properly.

**Needs your answer before anything else in §4 is actionable.**

## 5. Decision 3: readiness — entry point only
Readiness is being rebuilt by Komal and reused entirely, so POC should carry **the pill and where it lives**, and nothing behind it. That was already the 2026-07-31 decision and nothing has changed to reopen it.

Two things still need settling, both cheap:

- **The label.** POC says "Spotter readiness" (`ModelCanvas.tsx:2334`); Vision and Demo say "AI readiness". One name has to win, and POC's is the one that ships.
  
- **Where it lives.** Currently a pill in the canvas topbar. Confirm that's the entry point in the spec, since it's the thing engineering will wire her flow into.
  

Everything else about readiness stays out of POC scope until her merge lands.
