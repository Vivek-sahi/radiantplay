Grid as workbench — market scan & proposed interaction model

SearchDataOnDataModelFinal · 24 Sep 2026 · research across Tableau, Power BI, Looker, Omni, Sigma + fresh players (Hex, Lightdash, Count, Quadratic, Row Zero, Equals), then a proposal. All market claims from official docs; unverified items flagged in the per-player notes.

The question

ThoughtSpot's modeling canvas works at model level: the left panel is the inventory of the whole model, and it is the only creation surface (formulas, filters). That made sense when there was no live data in the canvas. Now the Split layout has a live preview grid with per-scope previews (model / table / join). Which creation and editing actions belong on the grid, and where do grid-born artifacts land?

Per-player notes (compressed)

Tableau — the closest structural parallel to us

A modeling canvas (relationships/joins) with a live grid below it — the same anatomy as our Split layout.

  • Column header menu on the Data Source grid: Create Calculated Field (pre-scoped to that column), Split / Custom Split, Create Group, Hide, Rename (double-click too), Describe, Copy Values, Pivot (multi-select columns → unpivot). Data type via the type icon in the header.
  • Everything lands in data source metadata — the model. On a published source, edits hit every workbook and user; Tableau's mitigation is a warning + "test in a scratchpad workbook first" + Publish vs Publish As (fork).
  • A metadata grid toggle flips the same surface from rows-of-data to fields-as-rows for bulk ops — the grid and the inventory are two states of one surface.
  • Value-level editing was deliberately excluded from the modeling canvas and shipped as a separate product (Prep: inline value edit, keep-only/exclude from cells, fuzzy grouping — every action recorded in an ordered, editable Changes pane).
  • Structural work stays off the grid: relationships, joins, data source filters, LOD calcs — canvas + dialogs.

Power BI — the recorded-step grid

Two grids, sharply split: Power Query (pre-load shaping, maximal) and Table view (post-load model inspection, partial).

  • Power Query grid: the same transform is reachable from ribbon, header menu, and right-click — deliberately. Header: filter/sort dropdown, type icon, double-click rename, drag reorder. Right-click column: remove, duplicate, add-column-from-examples, change type, transform (trim/case/round), replace values, split, group by, fill down/up, unpivot. Right-click a cell: filter by this value, replace-values pre-filled with it. Column profiling under every header (quality bar, distribution) with quick actions on hover.
  • Every gesture becomes a named, reorderable Applied Step — the inventory. Nothing is ever a silent mutation.
  • No inline cell editing, by design. Users ask for it repeatedly; Microsoft's standing answer: refresh would wipe it, use Replace Values (a recorded step). The market's clearest statement that recorded transformation ≠ data editing.
  • Table view (inside the model editor): right-click header → New measure / New column / Rename / Hide; DAX formula bar above the grid, new column materializes immediately. No shaping here — that's PQ's job. Grid sort/filter are view-local only.
  • The web semantic-model editor has no data grid at all — and Microsoft's 2024–26 investment went to more model-authoring surfaces (Model explorer, TMDL/DAX code views), not toward making the row grid the model editor.

Looker → Omni — the cautionary tale and its answer

Same people, opposite bets. Looker walls the grid off from the model; Omni makes the grid the model's front door.

  • Looker: the Explore grid is rich at query level — shortcut calcs from the header gear menu (% of column, running total, rank…), custom fields, the new column menus (filter, pivot, sort, hide) — but nothing grid-born can ever reach LookML. Promotion = a developer manually re-creates it. This is Looker's most-complained-about gap ("modeling twice", "untangling LookML", self-serve gated on the data team) and literally Omni's founding pitch.
  • Omni: type = in the grid for Excel-syntax formulas (XLOOKUP across tabs, cell refs); column three-dot menu: filter, aggregates, timeframes, quick calcs, edit the field's model definition from the grid; right-click a pivot value → create filtered measure; joins from the field browser (workbook-scoped). Every action writes to a per-workbook model layer.
  • Governance is a separate, explicit step: changes drawer → summary + color-coded YAML diff → "Promote to shared" (or add to an auto-created branch), gated on Modeler/Admin permissions.
  • Their thesis, verbatim: "Explore first, then model what matters." Customer evidence (Synthesia): business users define metrics in the UI, the data team reviews in a git workflow.

Sigma — the modeling canvas IS the grid

Datasets are dead (June 2026); the data model editor is a workbook page. Same gestures for exploring and modeling — the document type + publish step is the governance boundary.

  • Formula bar in the Excel position; column-level formulas ([Price] * [Quantity]) compiled to warehouse SQL.
  • Header caret menu: add new column (opens formula bar), duplicate, sort, filter, set aggregate, truncate date, format, totals, group. Rename = double-click. Add column via lookup = a join expressed as "add a column" — their most-copied gesture.
  • Dual entry is deliberate: columns/groupings are reachable from both the header menu and the right-side element panel. A grid-shaped thought never requires a panel round-trip.
  • Model-level extras live on the document: relationships (ERD view), metrics, "Visible as source" per element, publish-time content validation warning about breaking downstream columns.
  • Known gaps: no column-level promote from workbook → data model (copy/paste is unsynced); the documented cost of grid freedom is metric divergence across workbooks — not formula chaos.

Five patterns that repeat

1 · Nobody protects the model by making the grid view-only.
Every modeling-adjacent grid is actionable. The only view-only grid (Tableau View Data) is an inspection pane — and even it was redesigned for being too static. Governance lives elsewhere: publish steps, diffs, permissions.
2 · Grid gestures are launchers; artifacts always land in a recorded, inspectable inventory.
Applied Steps, Prep's Changes pane, Tableau's Data pane, Omni's workbook model, Sigma's element panel. The grid and the inventory are two views of one state, and dual entry (same action from header menu and panel) is deliberate.
3 · Column-level actions are grid-born; structural actions stay on the canvas.
Calculated fields, filters, type changes, renames, splits, cleans → header menu / right-click, pre-scoped to the column. Joins and relationships → canvas + dialogs everywhere (Sigma's lookup-as-a-column is the one softening of this line).
4 · Raw cell mutation is universally excluded from model grids.
Power BI refuses it by design; Tableau shipped it as a separate product (Prep) with recorded changes; Sigma isolates it in input tables (explicit writeback). Recorded transformation, never silent edit.
5 · The frontier differentiator is the promotion ladder.
Query-scope → model-scope with review: Omni's YAML diff, Lightdash's dbt pull request. Looker's missing rung is its top complaint; Sigma's missing column-level rung is its known gap. But note who needs a ladder: tools whose grid lives in a consumption document. A grid inside the model editor (Tableau, PBI Table view) writes to the model directly and needs no ladder.

The analyst's mental model — your three questions

Grounded in the tools' own designs (which encode observed behavior), practitioner sentiment from the research, and standard SQL practice.

1 · Do they query as they build, or once the model is assembled?

As they build — at every step. Every tool in the scan is built around incremental validation: Power Query previews the data after each step; Sigma's join UI shows key match rates and a preview before you commit; Omni's whole thesis is analysis-before-modeling; a SQL analyst writes SELECT … LIMIT 100 between every clause they add.

The three validation moments, in order of frequency:

  • On table arrival — is this the right table, are the values sane (nulls, dupes, date range, test rows). This is why PQ puts quality/distribution bars under every header.
  • On every join — the single most important mid-build check: did rows fan out (duplication) or vanish (key mismatch)? This can only be diagnosed cheaply at the moment the join is made; found at the end, it means unwinding the whole model to find which join broke it.
  • At the end — a smoke test, not the primary validation: run 2–3 questions with known answers ("last quarter's revenue should be ~X") against the assembled model.

This maps directly onto our shipped preview options: per-table/per-join checks are the select-to-preview moments; the end smoke test is the model-scope moment. The build loop uses both.

2 · Filters — at the table as it arrives, or on the finished model?

Depends which of three kinds of filter it is — and analysts instinctively separate them:

  • Scoping / hygiene filters (the majority): table-level, on arrival. "Last 2 years only", "exclude test accounts", "closed-won only". They define what the model is, and applying them early makes every later join check and preview faster and cleaner. This is Tableau's data source filter, a PQ filter step on the source query, the WHERE in a SQL analyst's first CTE — and the practitioner rule behind it is Roche's Maxim: shape data as far upstream as possible.
  • Cross-table filters (a minority): model-level, after joins exist. "Only accounts that have at least one opportunity" needs the join to be expressible at all.
  • Consumption filters: not in the model. "Let the exec slice by quarter" is left for the answer experience, not baked in.

So for the GTM story: the all-time opportunities table gets its date filter the moment the analyst first previews it — that's precisely a grid-at-table-scope gesture.

3 · Formulas — single-table or across the model?

Two populations, and every tool's type system splits them the same way:

  • Row-level derivations — the majority, single-table, often single-column, born early. Deal-size bands, name concatenation, quarter-of-date, flags like is_won, unit conversions. They're born the moment the analyst looks at a column and sees it isn't analysis-ready — which is why every tool's column menu has "Create calculated field" pre-scoped to the clicked column. (Power BI: calculated column · Tableau: row-level calc · Lightdash: custom dimension.)
  • Aggregate business metrics — the minority, high-value, often cross-table, born late. Win rate, pipeline coverage (opportunities × quotas), CAC (spend × customers). These need the joins to exist and are aggregations, not row math. (Power BI: measure · LookML: measure · Lightdash: custom metric.) They're created at model scope, after assembly — and they're the artifacts governance fights are about (Sigma's metric divergence).

The GTM walkthrough, end to end

Drop opportunities → preview it (table scope) → values look right, but it's all-time → filter close_date on the grid → and while looking at amount, add the deal-band formula from its column menu. Both land on that table in the model; the left panel shows them immediately.
Drop accounts, draw the join → preview the join (join scope) → row count looks right, no fan-out → move on. (If it fanned out: fix it now, while the cause is one join old.)
Drop reps, quotas — same loop per table: arrive → inspect → clean/scope → join → verify.
Model scope → smoke test → now create the cross-table metrics (win rate, coverage) at model scope, where they belong.

Proposal — the interaction model

One spine rule, then five supporting rules. All of it follows the market patterns above; none of it requires new machinery beyond what the Split prototype already has.

Spine
The scope you're previewing is the scope you're creating in. A filter or formula born while previewing opportunities is a table-level artifact on opportunities. Born at model scope, it's a model-level artifact (the cross-table metrics). The scope switcher we already built gives every grid-born artifact its scope for free — no extra chrome, no "where should this live?" dialog.
1
Grid actions write to the model directly — no staging layer. Omni and Sigma need promotion ladders because their grids live in consumption documents. Ours lives inside the model editor — the Tableau Data Source page / PBI Table view situation — where direct writes are the established pattern. The left panel inventory updating instantly is what makes direct writes feel safe.
2
Dual entry, always. Everything grid-born stays panel-born too (Sigma's explicit principle; PQ's ribbon/menu equivalence). The grid never becomes the only path — it's the in-context path. The column menu's job is to launch the existing creation flows pre-scoped to the clicked column, not to grow parallel flows.
3
No inline cell editing — recorded actions only. The market's firmest consensus. Our Clean ops (fix nulls, change type, replace value, text case, trim) are exactly the sanctioned form: a recorded, inspectable action on a column, never a silent mutation of a cell.
4
The grid shows model state back. The fx badge and filter-funnel tints we already have are the start; a rename or type change done on the grid should read as model metadata, same as if done in the panel. Grid and panel are two views of one model.
5
Structural work stays on the canvas. Joins and relationships remain canvas gestures (market-uniform). The grid's join contribution is verification — the fan-out check at join scope — not creation.

As built (24 Sep) — the two creation options

Ruled by Vivek: build both, demo both, document what each one costs. Switcher: Settings → Options → "Creation from preview (Split)". The machinery underneath is shared — the fx formula bar and the product's "Select value for :" filter dialog (copied from the MVP's replica, 25 Sep: date rolling/fixed with the resolved Preview chip, number operators, string/boolean value lists; real row predicates) write into the same model stores the left panel's Formula and Filters docks render. Creation is model-preview only (25 Sep ruling) — at table/join scope the triggers grey out with "Allowed in model preview". Filters and formulas actually filter/compute the preview rows. Promotion state colours (25 Sep): grey = applied to the preview only, blue = added to the model (funnel and fx chip). Promote at creation (checkbox + ⓘ in the modal / fx bar checkbox), later (funnel menu / fx column ▾ "Add to model"), or at save (the review modal). (History: 24 Sep first build used an include/exclude values popover, then the Combined sheet's two-step modal; both superseded — the popover remains unused in Spreadsheet.tsx.)

Option 1 · Adds to model directly default

Commit = model write. Formula commits land in the Formula dock, filter Applies land in the Filters dock. No checkbox anywhere.

  • Pros: one mental model — the canvas is the model editor and the grid is part of it; zero extra steps; grid and left panel can never disagree; the Tableau Data Source page / PBI Table view precedent; nothing half-in, half-out to explain.
  • Cons: no sandbox — every experiment is a model edit (undo = delete); a filter created "just to look at the rows" still lands in the model; a mis-click has model-level consequences.
  • Edge cases (few): deleting the artifact from the left panel leaves its column/filter in the preview, now amber — the column survives as a local leftover in a mode that has no draft concept. Rename/delete from the grid sync to the panel (built); the reverse direction only demotes.

Option 2 · Draft in preview · promote to model

Creation lands as an amber preview-local draft. "Add this filter to this model" checkbox in the Add-filter modal; "Add to model" checkbox in the fx bar (the formula's edit view — select the fx column and the same box promotes/demotes later); "Add to model / Remove from model" also in the fx column's ▾ menu. Drafts survive scope switches.

  • Pros: a sandbox — explore without touching the model; every model write is explicit intent; it's Omni's staging thesis in miniature, and the team's requested pattern.
  • Cons: a half-state ("in my preview but not in my model") inside the model editor; two states to teach; a user who never notices the checkbox ships a model missing their work.
  • Edge cases (the bloom):
    1. The preview lies — a draft filter changes the rows on screen while the model has no such filter; the amber funnel is the only tell. At model scope the preview no longer shows what a consumer of the model would get.
    2. Draft lifetime — survives scope switch and panel close (ruled + built); dies on reload. Unruled: should drafts persist with the model document itself?
    3. Out-of-scope drafts — a draft filter whose column leaves the current scope goes inert (rows stop filtering) and silently reactivates when the column returns. Built that way so a scope switch can't filter everything to zero, but it's still a surprise.
    4. The skipped checkbox — mitigated by the after-creation paths (▾ menu, edit view), but the user has to discover them.
    5. Publish-time sweep — BUILT (25 Sep, Vivek's ruling): "Save changes" opens a review modal — model name, description, and every unpromoted sheet filter/formula with an add-to-model checkbox (default checked). Omni's changes-drawer is the market precedent.
    6. Demote vs delete — unchecking removes the artifact from the model but keeps it in the preview; deleting the column removes both. Two removals, one artifact.
    7. Name collisions — model formulas are keyed by name, so promoting a draft named like an existing formula replaces it. Same rule as the modal editor, but easier to hit with casual grid names ("Formula 2").

Shared edge cases (both options): a model-level formula's values are still scope-local — switch to a scope missing its referenced columns and it shows empty/zero rows. And the stale-refresh machinery listens to canvas changes (tables/joins), not grid-born artifacts — a grid-born model write never raises "Data changed — Refresh" because the grid already shows the result.

The formula-language question (24 Sep, later)

The gap Vivek raised: the grid's fx bar speaks Excel (SUM, SUMIF, VLOOKUP, = entry — verbatim from the Spreadsheet Figma) while the left panel's Formula Editor speaks the ThoughtSpot formula language (its spec even lists Connection passthrough). Product ground truth, verified against docs.thoughtspot.com 26.9.0.cl (Sep 2026):

  • The shipped product chose one language. The core "Spreadsheet on live data" mode (Early Access, 26.9.0.cl) is explicitly ThoughtSpot-native: docs verbatim — "Functions use lowercase names and reference columns in square brackets, for example sum([Revenue]). Excel-style syntax (such as SUM(A:A)) is not supported in this release." Entry is an fx toolbar button / column-header +, not =. Spreadsheet ergonomics, TS language.
  • Same language at both levels already: Answer formulas and Model formulas use the identical language, editor and Formula Assistant — only scope differs (sum (revenue), if (cost > 500) then 'flag' else 'approve', group_aggregate(…), sql_…_op passthroughs).
  • But no promotion exists in the product: spreadsheet-mode formula columns "are stored in the Answer, not in the Model… not visible to other users"; Model formulas are "not reusable" outside their Model; the standing guidance is manual re-creation. The product today has the Looker wall — which is precisely the gap this exploration's two landing options address.
  • The Excel-ish signals live elsewhere: Analyst Studio's spreadsheet (Mode-derived, Jul 2026 EA) markets "SUMIF, VLOOKUP-style lookups" alongside group_aggregate — its exact entry syntax is undocumented (flagged unverified) — and Analyst Studio calculated fields are a third dialect (SQL-ish uppercase, [Status] brackets). Different surface, different persona (analyst prep), not the model editor.

Implication: "one language, two ergonomics" isn't just the market recommendation (PBI Table view, Sigma) — it's what core ThoughtSpot shipped this month. Aligning the prototype = swap the fx bar's Excel suggestion list for lowercase TS functions with [Column] refs, commit the same expression string the Formula Editor holds, and add "Edit in formula editor" to the fx column menu. The two-dialect option (grid Excel / panel TS) would put the prototype at odds with the shipped EA behavior. Awaiting Vivek's ruling.

Rulings so far (24 Sep)

  • First principle agreed: act on what you see — the visible column is the launcher; switch scope to reach the rest; the editor sees the whole scope.
  • Both landing options built for stakeholder comparison; Vivek's own position is direct-to-model ("users will not intuitively understand" a promote step inside the model editor).
  • Promote-after-creation happens in the artifact's edit view (fx bar checkbox, ▾ menu, filter menu re-open) — built. The publish-time sweep stays a documented variant.
  • Unpromoted artifacts get their own colour (amber) — built. Drafts survive scope switch — built. The draft-filter "preview lies" hazard is accepted with the amber marker as the tell.

Still open — your call

  • Chrome → real: the column menu's visual-only items (Rename, Duplicate, Format, Conditional formatting, Text wrapping). In market terms Rename and Format are model metadata (Tableau/PBI both grid-launch them). Which become real, in what order? (Grid rename of a base column is currently view-local.)
  • Join scope: creation actions at join-scope preview too, or only table + model scopes? (Market precedent is thin — join previews are for verification everywhere.)
  • Fan-out feedback: Sigma shows join-key match rates at join time. A row-count / match-rate readout in the join-scope preview — this exploration or later?
  • Model-scope metrics: when a cross-table formula is born at model scope, does it start from the grid at all (no single home column) or does model scope keep creation panel-first?
  • Option 2 only: draft persistence beyond the session, and the publish-time sweep.
