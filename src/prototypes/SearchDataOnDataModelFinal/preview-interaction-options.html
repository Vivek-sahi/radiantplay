Data preview — two mental models

SearchDataOnDataModelFinal · Split layout · 23 Sep 2026 · both are live in the prototype: Settings → Options → "Data preview (Split)". The question: does the preview work for the user automatically, or at the user's command?

Rules shared by both

  • The preview panel's scope dropdown always offers Model, every table, and every join.
  • The panel is the user's: closed by default, stays open once opened, never opens itself on a plain canvas click.
  • Error states are the same everywhere: no tables → "Add a table first". More than one table and not all joined into one connected model → "Model preview isn't available" — an error, never a partial result and never a query (a single lone table counts as a valid model). And if the table or join being previewed is removed from the model → "No longer in the model" — its own error, not "Nothing selected".
1Model is home · auto refreshcurrent default

The preview shows the model by default and keeps itself current. Clicking a table or join drills in; the model is one pick away in the scope dropdown (returns are instant, from the last result). When the model changes while its preview is showing, the grid re-queries on its own. Clicking the canvas background never touches the panel. The system works for the user.

Pros

  • The default state is useful — the model is on screen without asking.
  • Feedback at the moment of action: join two tables and the effect appears right where you're looking.
  • Fewest clicks for the common loop (do a thing → see the result: zero).
  • Creation actions get a natural home — the grid rests at model level, where formulas and filters live.
  • Always current — the preview never lies about the model's present state.

Cons

  • The grid moves on its own — responds to canvas actions without being asked, which can read as loss of control.
  • Queries fire automatically — cost is the system's judgement, not the user's.
  • Leans hardest on the model being valid — the broken-model error carries real weight.

Precedent: Sigma's workbook grid, Omni's create-where-you-work — the modern, model-centric direction.

2Select to preview · refresh on click

Nothing shows until the user selects something; every query traces to a click. Clicking a table or join (or its eye icon, which also opens a closed panel) previews it; a Preview model button by the zoom controls (plus the dropdown) reaches the model. Clicking the canvas background never touches the panel. When something being previewed is modified — a column removed, a join reconfigured, the model edited — the grid holds its rows and shows "Data changed — Refresh": the re-query is the user's click. The user commands the system.

Pros

  • Matches the current market's mental model — familiar on first touch.
  • User control as a tenet: what the user selects previews; what changed refreshes when they say so.
  • Query cost is entirely user-controlled — nothing runs uninvited.
  • The needs-refresh banner doubles as feedback: it says your action changed this data without presuming to act on it.

Cons

  • Every look at the data costs a click; the refresh costs another.
  • The preview can sit knowingly stale — correct only as of the last click.
  • The model is a destination to remember, not the ground; creation-from-grid has a weaker home.

Precedent: Tableau's data-source grid, Power BI's data view for selection; warehouse consoles (BigQuery, Databricks) and dbt for query-on-demand.

Two affordance variants, both clickable in the prototype: with eye icons on cards and join badges (they signal previewability and also open a closed panel; the card click previews too), or card click only (no icons — the selection itself is the ask, so a card/join click also opens a closed panel, inheriting the eye icon's opener role — 24 Sep). Same mental model either way; the demo can compare the affordance live. A third explored variant — icons as the only trigger, plain clicks never previewing — is built but off the menu; parked because it adds a click to the hottest loop and lets selection and preview disagree.

The dividing line

Earlier framings treated "where does the preview start" and "when does data update" as separate knobs. They collapse into one question because each answer only makes sense with its partner: a model that greets you but shows stale rows breaks its own promise, and a preview you summon click-by-click that then updates itself breaks the other one. Automatic is a package, and manual is a package. That's why there are two options, not a matrix.
